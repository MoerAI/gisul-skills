# 장별 핵심 가이드

이 문서는 Vladimir Khorikov의 *Unit Testing Principles, Practices, and Patterns* 1–11장을 실무 절차로 재구성한 요약이다. 원문을 대체하지 않으며, 정확한 문구나 사례가 필요하면 정식 판본의 해당 절을 다시 확인한다.

## 1장: 테스트의 목표

- 목표는 테스트 수가 아니라 장기적으로 기능 추가와 리팩터링 속도를 유지하는 것이다.
- 테스트도 작성·실행·수정·오탐 대응 비용을 갖는다. 보호 가치가 비용보다 큰지 본다.
- coverage는 미검사 영역을 찾는 보조 신호다. 목표 수치나 높은 비율을 품질 판정으로 쓰지 않는다.
- 개발 주기에 계속 실행되고 핵심 도메인과 중요한 위험을 겨냥해야 한다.

근거 절: 1.2, 1.3, 1.4.

## 2장: 단위 테스트의 정의

- 작은 행동을 빠르게 검증하고 테스트끼리 격리한다.
- 고전식은 테스트 간 공유 상태를 격리하고 실제 메모리 객체의 협력을 허용한다.
- 런던식은 SUT의 협력자를 대역으로 바꿔 클래스 단위 실패 귀속을 선호한다.
- 클래스 하나를 단위로 고정하거나 모든 의존성을 대역으로 바꾸지 않는다. 공유·가변·비결정·느린 특성을 분류한다.

근거 절: 2.1, 2.2, 2.3.

## 3장: 단위 테스트의 해부

- AAA로 한 행동과 그 결과를 읽히게 만든다.
- 반복 AAA, 조건문과 여러 Act는 시나리오 혼합 또는 API 캡슐화 문제의 신호다.
- assertion 개수보다 한 행동의 관련 결과를 충분히 검증하는지가 중요하다.
- 공통 fixture가 핵심 사전조건을 숨기지 않게 하고, 이름은 메서드보다 도메인 사실을 설명한다.
- parameterized test는 의미가 같은 데이터 변형에만 사용한다.

근거 절: 3.1, 3.3, 3.4, 3.5, 3.6.

## 4장: 좋은 테스트의 네 기둥

- 회귀 방지, 리팩터링 내성, 빠른 피드백, 유지보수성을 함께 평가한다.
- 내부 구현에 결합한 false positive는 시간이 갈수록 테스트 suite에 대한 신뢰를 무너뜨린다.
- E2E, trivial, brittle test 어느 극단도 이상적이지 않다. 위험과 비용에 맞는 조합을 택한다.
- black-box 관점으로 결과를 검증하고 white-box 정보는 테스트 누락을 찾는 데 보조적으로 쓴다.

근거 절: 4.1–4.5.

## 5장: Mock과 취약성

- stub은 입력 공급, mock은 외부로 나가는 동작 검증에 쓴다. stub과의 상호작용을 검증하지 않는다.
- public API와 관찰 가능한 행동은 같지 않다. 클라이언트 목표와 무관한 공개 요소는 구현 세부일 수 있다.
- 시스템 내부 통신은 대체로 구현 세부다. 시스템 간 통신이 외부 계약일 때 mock 검증이 가치 있다.
- 외부 프로세스라고 모두 mock하지 않는다. 애플리케이션이 소유하는 DB 같은 관리 의존성은 실제 상태로 검증할 수 있다.

근거 절: 5.1–5.4.

## 6장: 단위 테스트 스타일

- 출력 기반, 상태 기반, 통신 기반을 구분한다.
- 가능하면 순수한 결정의 입력·출력 검증을 우선하고, 의미 있는 최종 상태를 다음으로 선택한다.
- 통신 기반 검증은 외부에서 관찰되는 효과에 제한한다.
- 기능 코어와 변경 가능한 셸 분리는 테스트성을 높이지만 추가 조회, 성능과 코드량 비용을 함께 평가한다.

근거 절: 6.1–6.5.

## 7장: 가치 있는 테스트를 향한 리팩터링

- 복잡도·도메인 중요도와 협력자 수로 테스트 가치를 분류한다.
- 복잡하고 중요한 로직은 협력자를 줄여 단위 테스트하고, 단순 조정 코드는 소수의 통합 테스트로 다룬다.
- Humble Object로 프레임워크·I/O 조정을 얇게 하고 판단 로직을 분리한다.
- 도메인 이벤트나 CanExecute/Execute 같은 패턴은 결정과 외부 효과의 경계를 명시할 수 있지만 기계적으로 강제하지 않는다.

근거 절: 7.1–7.5.

## 8장: 통합 테스트가 필요한 이유

- 단위 테스트가 확인하지 못하는 구성, 실제 영속화와 외부 연동을 검증한다.
- 대부분의 경계 사례는 단위 테스트에 두고, 통합 테스트는 대표 성공 경로와 실제 경계에서만 드러나는 위험에 집중한다.
- 관리 의존성은 실제 인스턴스와 최종 상태로, 비관리 의존성은 대역과 외부 계약으로 검증한다.
- 인터페이스를 테스트 대역 하나를 위해 무조건 추가하지 않는다.

근거 절: 8.1–8.5.

## 9장: Mocking 모범 사례

- mock은 주로 통합 테스트에서 비관리 의존성과의 외부 계약을 확인한다.
- 검증 지점은 가능한 한 시스템 경계의 마지막 자체 어댑터에 둔다.
- 기대 메시지를 production helper로 다시 생성하지 말고 테스트에서 독립적으로 명시한다.
- 예상 호출의 내용·횟수와 예상하지 않은 추가 호출을 함께 확인한다.
- 소유하지 않은 제3자 타입보다 프로젝트가 소유한 어댑터를 경계로 삼는다.

근거 절: 9.1, 9.2.

## 10장: 데이터베이스 테스트

- 스키마와 기준 데이터를 버전 관리하고 개발자·실행 간 격리된 실제 DBMS를 사용한다.
- 운영 데이터가 존재하면 변경과 데이터 변환을 명시하는 migration 기반 전달을 우선한다.
- 업무 트랜잭션 경계를 production과 test에서 같게 유지한다.
- 일반 데이터는 각 테스트 시작 시 정리하고 기준 데이터는 보존한다.
- 다른 제품의 in-memory DB로 실제 공급자 동작을 대신했다고 주장하지 않는다.

근거 절: 10.1–10.4.

## 11장: 단위 테스트 안티패턴

- private method·state를 테스트용으로 공개하지 말고 관찰 가능한 결과를 검증한다.
- private 로직이 너무 복잡하면 죽은 코드인지, 독립 책임으로 추출할 대상인지 판단한다.
- 기대값 계산에 production 알고리즘을 복제하지 않는다.
- production 코드에 test-only 분기와 전역 시간 상태를 넣지 않는다.
- concrete class partial mock이 필요하면 외부 통신과 도메인 계산이 섞였는지 먼저 본다.

근거 절: 11.1–11.6.
