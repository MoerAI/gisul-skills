# 핵심 테스트 원칙

## 테스트의 목적

- 테스트의 목적은 테스트 수를 늘리는 것이 아니라 중요한 동작을 보호하며 변경 속도를 유지하는 것이다.
- 테스트도 작성·실행·수정·오탐 대응 비용을 갖는다. 보호 가치가 유지 비용보다 커야 한다.
- coverage는 실행되지 않은 영역을 찾는 보조 신호다. 높은 비율은 assertion이나 oracle의 품질을 증명하지 않는다.
- 핵심 도메인 규칙, 장애 시 손실이 큰 경로와 자주 변경되는 계약을 우선한다.

## 좋은 테스트의 기준

각 테스트를 네 축으로 평가한다.

1. **회귀 방지:** 중요한 코드와 결과를 실제로 검증한다.
2. **리팩터링 내성:** 동작이 같은 내부 변경에 불필요하게 실패하지 않는다.
3. **빠른 피드백:** 개발 흐름에서 반복 실행할 수 있다.
4. **유지보수성:** 준비, 이해, 수정과 환경 운영 비용이 감당 가능하다.

한 축이 심각하게 약하면 테스트의 전체 가치가 낮아진다. 테스트를 유지·개선·대체·제거할 때 네 축과 업무 중요도를 함께 본다.

## 단위 테스트 경계

- 하나의 중요한 행동을 빠르게 검증하고 테스트끼리 상태를 공유하지 않는다.
- 클래스 하나를 단위로 고정하지 않는다. 여러 메모리 객체가 함께 동작해도 테스트 간 격리가 유지되면 단위 테스트가 될 수 있다.
- 의존성을 공유 상태, 가변성, 비결정성, 속도와 환경 설정 기준으로 분류한다.
- 모든 협력자를 대역으로 바꾸거나 모든 실제 객체를 유지하는 식의 절대 규칙을 쓰지 않는다.

## 테스트 구조

- Arrange–Act–Assert로 사전조건, 행동과 결과를 읽히게 만든다.
- 반복 AAA, 조건문과 여러 Act는 여러 시나리오가 섞였거나 API가 업무 행동을 충분히 캡슐화하지 못한 신호다.
- assertion 개수보다 한 행동의 관련 결과를 충분히 검증하는지가 중요하다.
- fixture helper는 기술적 반복을 줄이되 핵심 입력과 차이를 숨기지 않는다.
- 이름은 구현 메서드가 아니라 검증하는 도메인 사실을 설명한다.
- parameterized test는 같은 사실의 데이터 변형에만 사용한다.

## 관찰 가능한 동작

- 반환값, 의미 있는 최종 상태와 외부 계약을 검증한다.
- public API라고 모두 관찰 가능한 계약은 아니다. 클라이언트 목표와 무관한 공개 요소는 구현 세부일 수 있다.
- private method·state, 내부 collection 모양과 내부 호출 순서에 테스트를 결합하지 않는다.
- black-box 관점으로 결과를 검증하고 white-box 정보는 누락된 경로를 찾는 데 보조적으로 사용한다.

## 테스트 스타일

- 가능하면 결정 로직을 입력·출력으로 검증한다.
- 의미 있는 결과가 상태 변화라면 최종 상태를 검증한다.
- 통신 기반 검증은 외부에서 관찰되는 효과와 호환성 계약에 제한한다.
- 숨은 시간·난수·전역 상태·I/O를 명시적인 입력과 경계로 바꿀 수 있는지 검토한다.

## 테스트 더블

- stub과 fake는 입력과 환경을 제공한다.
- mock과 spy는 외부로 나가는 관찰 가능한 효과를 기록한다.
- stub 호출 자체나 내부 collaborator 호출을 assertion으로 만들지 않는다.
- 애플리케이션이 소유하는 DB 같은 관리 대상 의존성은 실제 상태로 검증할 수 있다.
- 외부 시스템이 관찰하는 비관리 의존성은 시스템 경계에서 메시지·요청 계약을 검증한다.
- 기대값을 production helper로 다시 생성하지 않는다. 독립적인 oracle을 사용한다.

## 테스트 가능한 구조

- 복잡하고 중요한 로직은 협력자를 줄여 단위 테스트한다.
- 외부 입력 수집, 도메인 결정과 효과 적용을 분리한다.
- 프레임워크·DB·메시지 조정을 얇은 경계에 두고 핵심 판단을 메모리 안에서 실행 가능하게 만든다.
- 새로운 interface, event와 abstraction은 실제 변경·테스트 비용을 줄일 때만 추가한다.
- 테스트하기 쉬움은 좋은 설계의 충분조건이 아니다. 성능, 코드량과 운영 복잡도도 함께 평가한다.

## 통합 테스트

- 실제 DI, serialization, ORM mapping, transaction과 adapter 연결을 검증한다.
- 단위 테스트의 모든 edge case를 복제하지 않는다. 대표 성공 경로와 실제 경계에서만 드러나는 위험에 집중한다.
- 관리 대상 의존성은 실제 인스턴스와 최종 상태로 검증한다.
- 비관리 의존성은 대역 또는 contract test로 외부 계약을 검증한다.
- E2E는 전체 시스템 연결에서만 확인 가능한 소수의 고가치 경로에 사용한다.

## 데이터베이스 테스트

- production과 같은 DBMS 공급자와 중요한 설정을 사용한다.
- schema와 reference data를 version control과 migration으로 관리한다.
- 업무 transaction 경계를 production과 test에서 같게 유지한다.
- 각 테스트 시작 시 일반 데이터를 정리하고 reference data는 보존한다.
- 저장 후 실제 read path로 결과를 확인한다.
- 다른 제품의 in-memory DB 통과를 production DB 동작의 증거로 쓰지 않는다.

## 피해야 할 패턴

- 테스트를 위해 private API나 state를 공개한다.
- production 코드에 test-only 분기와 전역 hook을 넣는다.
- 기대 결과를 계산하며 production 알고리즘을 복제한다.
- concrete class의 partial mock으로 섞인 책임을 감춘다.
- 실제 시간, sleep, 실행 순서나 이전 테스트 데이터에 의존한다.
- 테스트 통과를 요구사항 완전성, 설계 품질 또는 운영 준비의 증명으로 확대한다.
