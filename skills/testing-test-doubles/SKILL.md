# Test Doubles and Mocks

## 1. 대역의 역할을 분류한다

- stub/fake가 SUT에 입력을 공급하는가.
- mock/spy가 SUT에서 외부로 나가는 효과를 기록하는가.
- 단지 내부 호출 그래프를 감시하는가.

stub 호출 자체를 assertion으로 만들지 않는다. 결과를 만드는 중간 과정을 고정하기 때문이다.

## 2. 경계를 분류한다

각 의존성을 다음처럼 기록한다.

- 프로세스 내부 또는 외부.
- 애플리케이션이 소유·관리하는지.
- 다른 시스템이 호출·메시지·공유 데이터 형태를 관찰하는지.
- 중복·순서·형식이 호환성 계약인지.

외부 프로세스라는 이유만으로 mock하지 않는다. 자체 DB처럼 관리 대상이면 실제 상태 검증을 우선할 수 있다.

## 3. 검증 지점을 고른다

- 외부 계약이면 시스템 경계의 마지막 자체 어댑터에서 요청·메시지를 검증한다.
- 기대값은 production 메시지 생성 helper를 재사용하지 말고 독립적으로 명시한다.
- 필요한 호출의 내용과 횟수, 허용되지 않은 추가 호출을 확인한다.
- 로그처럼 느슨한 계약에는 핵심 정보만 검증한다. 모든 외부 효과에 byte-level 동일성을 강제하지 않는다.

## 4. 취약성 신호

내부 collaborator mock, private 호출 검증, 정확한 내부 호출 순서, 광범위한 `verifyNoOtherCalls`, concrete partial mock은 구현 세부 결합 후보다. 실제 외부 계약 근거가 없으면 결과·상태 검증 또는 책임 분리를 검토한다.

## 보고

각 대역의 역할, 관리/비관리 분류, 관찰 가능한 계약, 검증 위치와 mock 때문에 미검증된 실제 동작을 명시한다.
