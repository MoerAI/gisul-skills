# Refactor for Valuable Tests

## 1. 코드를 분류한다

복잡도·도메인 중요도와 협력자 수를 기준으로 본다.

- 복잡하고 중요한 로직 + 적은 협력자: 단위 테스트 우선.
- 단순 로직: 별도 테스트 가치가 낮을 수 있다.
- 많은 협력자를 조정하는 단순 코드: 대표 통합 테스트.
- 복잡한 로직 + 많은 협력자: 분리 우선.

## 2. 결정과 효과를 분리한다

1. 외부에서 입력을 수집한다.
2. 도메인 객체나 기능 코어가 결정을 값·상태 변화·도메인 이벤트로 표현한다.
3. 얇은 셸 또는 application service가 DB, 메시지와 파일 효과를 적용한다.

Active Record, 서비스 로케이터, 숨은 clock처럼 도메인 판단 안으로 들어온 외부 접근을 찾는다. 인터페이스로 감싸기만 했다고 분리가 끝난 것은 아니다.

## 3. 절충을 기록한다

기능적 구조는 추가 조회, 코드량과 성능 비용이 있을 수 있다. CanExecute/Execute, domain event와 새 abstraction은 실제 조건 분리와 외부 효과가 있을 때만 도입한다. 미래의 테스트 편의를 위해 무조건 만들지 않는다.

## 검증

분리 전후 동일한 관찰 가능 행동을 회귀 테스트로 확인한다. 코어의 출력·상태 테스트와 셸의 통합 테스트가 각각 어떤 계약을 담당하는지 보고한다.
