# Unit Test Design

## 절차

1. 테스트가 보호하는 도메인 행동을 한 문장으로 적는다. 클래스나 메서드 이름만 반복하지 않는다.
2. SUT, 값 객체, 협력자와 공유·가변·비결정·느린 의존성을 분류한다.
3. 테스트끼리 상태를 공유하지 않게 격리한다. 여러 실제 메모리 객체를 함께 쓰는 것 자체는 결함이 아니다.
4. Arrange–Act–Assert를 구분하고 Act는 하나의 업무 행동으로 유지한다.
5. Assert는 반환값, 최종 상태와 필요한 외부 효과 중 계약에 해당하는 결과를 충분히 확인한다.
6. 테스트 이름과 실패 메시지만으로 깨진 도메인 사실을 찾을 수 있게 한다.

## 리뷰 규칙

- 반복 AAA, 조건문, 여러 Act가 있으면 시나리오를 분리한다. 단, 동일 행동의 연속 상태가 계약인 workflow test는 별도로 분류한다.
- 다단계 Act가 필요하면 공개 API가 불변식을 클라이언트에게 떠넘기는지 확인한다.
- fixture helper는 기술적 반복을 숨기되 핵심 입력과 차이를 호출부에 남긴다.
- 생성자·base fixture가 테스트별 사전조건과 수정 영향을 숨기지 않는지 확인한다.
- parameterized test는 같은 사실의 데이터 변형에만 사용한다. 의미가 다른 성공·실패를 한 표에 합치지 않는다.
- assertion 하나 규칙을 강제하지 않는다. 하나의 행동이 만든 관련 결과는 함께 검증할 수 있다.

## 완료 증거

테스트별 보호 계약, 격리 방식, AAA 경계, 핵심 assertion, 실행 결과와 남은 미검증 범위를 보고한다.
