# Integration Testing

## 1. 단위 테스트의 공백을 찾는다

실제 DI·serialization·ORM mapping·transaction·filesystem·network adapter와 외부 계약 중 단위 테스트가 확인하지 못하는 것을 적는다. 통합 테스트를 단위 테스트의 모든 edge case 복제본으로 만들지 않는다.

## 2. 대표 시나리오를 선택한다

- 외부 의존성을 가장 넓게 통과하는 중요 성공 경로.
- 실제 경계에서만 드러나는 실패·호환성·원자성 위험.
- Fail Fast로 상태 오염 없이 즉시 드러나는 사소한 검증 오류는 낮은 층에 둔다.

한 성공 경로가 모든 경계를 지나지 않으면 필요한 만큼만 추가한다.

## 3. 의존성을 다룬다

- **관리 대상:** 애플리케이션이 단독 소유하는 DB·저장소 등은 실제 인스턴스를 사용하고 저장 후 다시 읽어 최종 상태를 검증한다.
- **비관리 대상:** 외부 메시지 버스·서비스처럼 다른 시스템이 관찰하는 계약은 대역 또는 contract test로 검증한다.
- 공유 DB의 외부 소비 테이블처럼 한 의존성 안에서도 경계가 섞일 수 있다.

실제 관리 의존성을 쓸 수 없으면 mock 기반 테스트를 곧바로 통합 테스트라고 부르지 말고 확보하지 못한 신뢰를 명시한다.

## 4. E2E 범위를 정한다

통합 테스트가 실제 관리 의존성과 외부 계약을 충분히 다루면 E2E는 전체 시스템 연결에서만 확인 가능한 소수의 고가치 경로로 제한할 수 있다. 배포·routing·인증이 핵심이면 실제 배포 환경을 쓰고, 그렇지 않으면 로컬·CI의 배포 유사 환경도 가능하다. 실행 환경보다 검증 주장의 범위를 정확히 적는다.
